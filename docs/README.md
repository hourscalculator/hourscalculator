# Time Card Calculator 产品需求说明（总览）

> 文档版本：V1.0｜整理日期：2026-11-15｜语言：中文（网站界面继续使用英文）  
> 线上参考：https://hourscalculator.boardgamefun.workers.dev/  
> 文档用途：以后修改产品需求，先修改这些 Markdown，再交给 Codex 实现。本文不规定技术栈。

## 1. 这是一款什么产品？

用户填写上班、下班与休息时间，网站计算工时；如填写时薪，还能估算工资。可以按周、双周或其他日期范围查看，支持多人记录、打印、CSV 导出和分享报告。

**产品原则：首次使用尽量简单；复杂工作安排仍有完整入口。** 普通用户可通过四步向导填写；高级用户可用 Detailed（详细填写）。两种填写方式使用同一份数据，最终进入同一套 Report（结果报告）。

### 四类典型用户

| 谁在使用 | 想完成什么 | 最常见操作 | 主要入口 |
| --- | --- | --- | --- |
| 小时工 | 核对这周上了多少小时、估算收入 | 周一至五填统一时间，偶尔改一天 | 手机、快速填写 |
| 自由职业者 | 给客户核对工作记录、准备开票 | 一天几段工作，记录客户/项目 | 电脑、详细填写 |
| 小老板 / HR | 核对一周或两周工时及加班费 | 检查日期、休息、加班规则 | 电脑、详细填写 |
| 小团队负责人 | 一次核对多名人员的工时 | 每人一张卡，查看合计 | 电脑、详细填写 |

## 2. 怎么看这份 PRD

这套文档刻意分成两层，避免把“线上已经存在”和“准备修改”混淆：

- **【线上可核对】**：2026-11-15 从公开网页内容、帮助和可见入口核实的功能；不代表所有按钮都已人工点测。
- **【旧PRD记载】**：四份上传的旧文档已有要求，但本次无法从网页静态内容证明交互完全符合描述。
- **【本次确认的目标】**：你在本次会话作出的选择。即使当前网站尚未实现，也应当作为下一轮修改依据。
- **【待核实】**：存在冲突、缺少可见证据或细节尚未确定。不得凭空认定为现状。

**执行顺序**：先完整保留线上功能基线，再叠加“本次确认的目标”。开发时不得因为简化首屏而删除高级功能。

## 6. 所有页面共用的计算规则

下文统一用“工时”表示可以计入计算的净工作时间。

### 6.1 工作时间和休息

1. **当日净工时 = 当日各段工作时间之和 − 工作段内的无薪休息时间**。
2. 有薪休息仍算工时；两段工作之间没工作的间隔无需再扣一次。
3. `09:00–12:00` 和 `13:00–17:00` 是 **7小时**。若 `09:00–17:00` 另有 **30分钟无薪休息**，是 **7小时30分钟**。
4. 下班时间早于上班时间表示跨到第二天；相同时间视为无效的零时长班次。
5. **自动休息的线上说明**：在中午生成可编辑的无薪休息时间段；用户手动编辑休息后，自动休息会关闭。必须避免同一段休息重复扣除。
6. 时间计算使用实际输入的分钟；不使用经过四舍五入的展示值来反算工资。

### 6.2 工时展示

- 同一工时要同时能看 `hh:mm` 和 `Decimal`。例如 `7:30 = 7.50小时`、`24:03 = 24.05小时`。
- 修改小数显示精度或按15分钟的**显示舍入**，不得改变实际工时和工资计算。
- 线上帮助说明按本地日历日期与钟表分钟处理，不做设备时区换算；夏令时切换不自动修正。

### 6.3 加班和工资

**新建快速填写默认关闭加班。** 详细模式在旧PRD里记载新建默认“周超40小时”；是否与实际首页默认一致，仍须实机核验。已有草稿切换模式时，保留它原有的加班设置。

| 模式 | 计算方式（线上帮助说明） |
| --- | --- |
| 不计算加班 | 所有净工时按普通时薪计算 |
| Weekly | 每个工作周超过40小时的部分按1.5倍计算；双周不把80小时作为单一门槛 |
| Daily | 每个工作日超过8小时的部分按1.5倍计算 |
| California | 超过8至12小时按1.5倍，超过12小时按2倍；另考虑连续第七个工作日与工作周规则，避免重复计算同一加班溢价 |

- 统一时薪可留空：不填也能得到工时，金额显示“未设置时薪”，不能当作零工资。
- 工资估算基于实际分钟与所选时薪，最终按货币最小单位（如美元分）处理。
- 统计范围外若有影响同一工作周加班的相邻工时，应参与计算；结果只展示选择范围内的记录，并在缺少上下文时提示估算可能不完整。
- 网站提供的是**估算的税前工资**，不处理税、奖金、特殊行业豁免、meal penalty 等情形。

## 7. 数据、分享及安全边界

- 【线上可核对】草稿保存在当前浏览器；清理浏览器数据或无痕模式可能导致丢失。当前不要求登录、跨设备同步或服务端账户。
- 【线上可核对】分享时把当次记录做成**只读快照链接**。持有链接的人可以阅读快照；链接不能撤销，也不自动随本地修改更新。
- 【线上可核对】审批回执由链接持有人填写并生成回执链接，**不验证真实身份**；不能描述为带身份认证的电子签名。
- 【本次确认的目标】两种填写方式、所有卡片和报告必须共用一套输入/计算结果；修改统一时薪后全部卡片重新计算。
- 清空或覆盖已有工时要有明显警告；取消时原数据不变。无效输入必须提示错误，不应生成有误导性的可交付报告。

## 8. 页面体验要求

- 手机首屏首先呈现工具入口与必要输入，不让长篇帮助说明挤在操作区前面；说明和 SEO 正文可保留在主要操作区后方。
- 第一次访问自动弹出四步向导；之后首页有明显“快速填写”按钮，Detailed 和 Advanced settings 仍可找到。
- 高级设置默认折叠；展开后保留全部已有功能。
- 手机上能点击、输入、返回、展开逐日详情，不依赖悬停；时间轴之外必须能用文字输入时间。
- 输入错误应指出具体日期和字段，不仅显示一个笼统的失败提示。

## 9. 整体验收：四类用户各跑一次

以下是产品验收示例，不等于已经在网页逐项测试通过。详细步骤在各子 PRD。

| 编号 | 场景与输入 | 正确结果 |
| --- | --- | --- |
| TC-01 小时工 | 周一至四 `08:00–16:30`、各休30分钟；周五 `08:00–18:00`、休30分钟；$20/h；打开 Weekly 加班 | 周总 **41:30**；普通40小时=$800；加班1:30=$45；共 **$845** |
| TC-02 自由职业者 | 周一 `09:15–11:45` + `12:30–15:00`；周二 `10:00–12:00` + `13:00–16:15`；$75/h；不计加班 | 周一5:00、周二5:15；总 **10:15 / 10.25h / $768.75** |
| TC-03 HR | 两周周一至周五 `09:00–17:30` 各休30分钟，第二周周五改 `09:00–19:30`；$22/h；Weekly | 第一周40小时，第二周42小时；普通80小时、加班2小时；总 **82小时 / $1,826** |
| TC-04 团队 | Alex `07:00–15:30`休30；Ben `07:30–16:00`休30；Chris `08:00–17:00`休60；三张卡，同一天，统一$25/h | 每人均8小时/$200；合计 **24小时/$600** |

TC-04 逐人核对：Alex 8.5−0.5=8；Ben 8.5−0.5=8；Chris 9−1=8。合计24，避免漏算其中一张卡或休息重复扣除。

## 10. 尚未确认、不要默默改写的事项

| 编号 | 问题 | 当前处理方式 |
| --- | --- | --- |
| OPEN-01 | 旧README说自动休息“达到阈值后仅补足手动无薪扣除差额”；线上说明说“中午生成可编辑时段，编辑后关闭自动” | **以线上公开说明记录基线**；真实边界行为待实机验证；不混用两套算法 |
| OPEN-02 | 快速填写切换新周时，除上下班时间外是否复制休息分钟、逐日工作内容 | **只把复制上下班时间列为确定需求**；其余不新增隐含复制行为 |
| OPEN-03 | 从一周改为双周或自定义日期时，如何推导“上一周”的模板 | 保留现有可选日期功能；新增的“复制上周”规则只覆盖切换到**新的一周** |
| OPEN-04 | 四步向导、确认弹窗、模板预览等完整操作是否已与旧PRD一致 | 静态页面不足以证实，作为验收项目，不写成已实测通过 |
| OPEN-05 | 旧报告文档支持每卡不同费率，与你已决定的“全卡统一费率”冲突 | **统一费率为本次最终目标**；旧“每卡单独费率”不再用于新建、编辑界面 |

## 11. 以后怎样修改 PRD 并交给 Codex

1. 找到对应文件、对应需求编号，直接修改**用户操作 → 应当看到的结果 → 验收示例**。
2. 在文件的“变更记录”追加日期、需求编号与修改内容；不要只在聊天里口头修改。
3. 若修改全局规则（时薪、加班、分享等），同时检查其他 PRD 是否受影响。
4. 让 Codex **先列出需求差异与受影响页面，再修改代码，最后运行对应验收用例**；不要以旧代码行为反向覆盖新需求。
5. 需求尚未明确时，标注 `待确认`，不要让 Codex 自行猜规则。

可直接复制给 Codex 的提示词：

> 请以 `README.md`、`quick-fill.prd.md`、`detail.prd.md`、`report.prd.md` 为产品需求依据。先阅读“需求状态”和变更记录，列出现有代码与【本次确认的目标】的差异，说明受影响页面及现有功能的回归风险，再按对应验收用例实现。不得擅自删除已列为保留的高级功能，不得把【待核实】当作已确认规则。修改完成后报告各测试的通过/失败情况。
